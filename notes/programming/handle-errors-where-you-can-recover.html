Good Python error handling is not mainly about knowing the syntax of try and except. It is about deciding which layer has enough context to respond meaningfully to a failure. The central rule is: catch an exception only where the program can make a useful decision about it. If the current function cannot recover, let the exception travel upward.

Not catching can be correct handling

Imagine an HTTP endpoint calling create_user(), which calls save_user(), which calls the database. If PostgreSQL is temporarily unavailable, save_user() probably cannot repair it. Catching the failure there merely to print a message does not make the operation succeed: 

def save_user(user):
    try:
        database.insert(user)
    except DatabaseError:
        print("Something went wrong")

Unless the function can retry safely, use another store, or otherwise restore a valid outcome, the simpler version is usually more honest: 

def save_user(user):
    database.insert(user)

Python will automatically offer the exception to each caller in turn. This code is not ignoring the error. It is saying, “this layer cannot decide what to do; a layer with more context must decide.” The eventual handler might return an HTTP 500, retry a background job, show a dialog, or terminate a CLI command. Those are application decisions, not database-helper decisions.

Ask forgiveness, but do not catch everything

“Look before you leap” (LBYL) checks whether an operation appears safe before doing it. “Easier to ask forgiveness than permission” (EAFP) attempts the operation and responds if it fails. Deleting a file shows why EAFP is often stronger: 

# LBYL
if os.path.exists(path):
    os.remove(path)

# EAFP
try:
    os.remove(path)
except FileNotFoundError:
    handle_missing_file(path)

The LBYL check can become false between the check and the removal, and existence is only one possible problem. Permissions, a read-only filesystem, or a directory at that path can still make the operation fail. The operation itself is the final authority on whether it succeeded.

EAFP does not mean wrapping every call in except Exception. Catch only failures you expect and can handle. A broad catch can turn a programming bug such as a NameError into a misleading “user not found” result: 

try:
    user = get_user()
except UserNotFound:
    return None

Here an expected UserNotFound changes the program's path, while an unexpected bug still produces a traceback. Specific catches protect the distinction between an anticipated failure and broken code.

The four cases

Two questions classify almost every error-handling decision. First, did this function discover a new problem, or did a called function raise it? Second, can this layer recover and continue with a valid result?

Recoverable here Not recoverable here
This code detected it Correct it locally and continue Raise an exception
Called code raised it Catch it, recover, and continue Let it bubble up

New and recoverable: correct it locally

If a missing song year has a legitimate default, use it. No other layer needs to participate in a decision already made: 

if song.year is None:
    song.year = "Unknown"

An unusual condition does not automatically need an exception. Raise only when the current layer needs somebody else to decide.

Bubbled up and recoverable: catch and take the alternative path

A lower-level failure can be meaningful control flow when the caller knows the fallback: 

try:
    artist = get_artist_from_database(song.artist)
except NotFound:
    artist = add_artist_to_database(song.artist)

This is genuine handling. The exception has been consumed because the program now has a valid artist and can continue. Logging alone is not recovery; choosing a valid alternative is.

New and not recoverable: raise

If a function discovers that it cannot fulfill its contract, it should stop and tell its caller: 

def register_user(user):
    if user.email is None:
        raise ValueError("email is required")

The condition is non-recoverable for register_user(), but it may be recoverable for an HTTP endpoint that turns it into a 400 response. Recoverability is relative to a layer, not an intrinsic property of the error.

Bubbled up and not recoverable: let it travel

If a called function fails and the current function has no valid fallback, the best implementation may contain no error-handling code at all: 

def new_song():
    song = get_song_from_user()
    add_song_to_database(song)

If the database is offline, new_song() cannot fix it. Adding a catch that only prints “database failed” couples business logic to a console and discards the richer traceback. Letting the exception bubble preserves both the failure and the freedom for a higher layer to present it appropriately.

Why the outer boundary is different

Catching Exception deep in business logic can hide bugs. At the outer boundary of a unit of work, however, a broad catch can be appropriate because the application finally knows what every escaped exception means: this request, job, event, or command failed. 

try:
    run_cli()
except Exception:
    logger.exception("Command failed")
    sys.exit(1)

A web framework can perform the equivalent operation for each request: log the traceback, return a generic 500 response, clean up request-scoped resources, and keep the server alive. A worker can mark a job failed and schedule a retry. This is why generic handling belongs at boundaries instead of being duplicated throughout the call stack.

except Exception also intentionally leaves some process-control signals alone. KeyboardInterrupt and SystemExit inherit directly from BaseException, so an ordinary catch-all does not normally interfere with them.

Handling, observing, and swallowing are different

A catch can serve very different purposes:

# Handle: produce a valid alternative and continue.
try:
    config = load_config()
except FileNotFoundError:
    config = default_config()

# Observe: add useful context, then preserve the failure.
try:
    process(order)
except ProcessingError:
    logger.exception("Processing order %s failed", order.id)
    raise

# Swallow: claim success when the program may be broken.
try:
    process(order)
except Exception:
    pass

Logging does not by itself handle an exception. If this layer cannot recover after recording it, re-raise it. Silencing a broad class of failures is dangerous because it erases the signal that anything went wrong.

Translate at real abstraction boundaries

Sometimes a layer cannot recover but should prevent implementation details from leaking into its public contract. A service may translate a database-driver error into application language while preserving the original cause: 

try:
    repository.save(user)
except PsycopgError as error:
    raise UserStorageError("Could not store user") from error

Translation is not recovery; the operation still failed. It is useful when callers should depend on UserStorageError, not on whichever database driver is currently installed. Do this at genuine abstraction boundaries, not mechanically at every level, or the code becomes a stack of wrappers that add no information.

A practical decision rule

  1. If this layer can produce a valid outcome, catch or correct the problem and continue.
  2. If this layer discovers an invalid condition it cannot resolve, raise an appropriate exception.
  3. If called code fails and this layer cannot recover, usually let the exception bubble untouched.
  4. At a real abstraction boundary, translate the exception if callers should not know the implementation detail.
  5. At the application's outer boundary, log or report unexpected failures and fail that unit of work safely.

The question that unlocks the whole subject is not “where should I put try/except?” It is “which layer has enough information to make a sensible decision about this failure?” Put the handler there. Everything below it can remain straightforward business logic, and unexpected bugs retain the tracebacks that make them diagnosable.
