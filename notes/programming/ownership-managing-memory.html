A running program borrows memory to hold its data, and it has to give that memory back when it is done, or it slowly eats all the memory on the machine. How a language handles this hand-back is a surprisingly deep design choice, and there are three broad answers.

Two classic answers, each with a cost

The first answer is to make the programmer give memory back by hand: you asked for it, you release it. This is fast and gives you total control, but it is a minefield. Forget to release something and it leaks. Release it twice, or keep using it after releasing it, and you get crashes or subtle corruption. A huge share of serious bugs and security holes over the years come from exactly these mistakes.

The second answer is to hire a helper that runs alongside your program and automatically reclaims memory nobody is using anymore. This is safe and convenient, and you stop thinking about the problem. But the helper is not free: it uses processing time, and it can pause your program at inconvenient moments to do its sweep.

A third answer: single ownership

There is a third way. Give every piece of data exactly one owner. When that owner goes out of use, the data it owns is automatically cleaned up. Because there is always exactly one owner, it is never ambiguous who is responsible for releasing something.

The clever part is that this can be worked out ahead of time, before the program ever runs. Since ownership rules are fixed and checkable, the cleanup can be placed automatically where each owner ends, with no background helper and no manual bookkeeping. You get the safety of automatic cleanup without the runtime cost of a helper watching over you.

The catch, and why it is worth it

Nothing is free. With single ownership, passing data around means passing ownership along with it, or explicitly lending it out for a while. That takes some discipline, and it forces you to be clear about who holds what. In return, you get memory safety with no runtime penalty, which is a genuinely good trade for programs that need both speed and reliability.

The idea travels

Although this comes from managing memory, the principle reaches further. Tying a resource's lifetime to a single owner works for anything you must release: open files, network connections, locks. Whenever cleanup matters, "exactly one owner, cleaned up when the owner is done" is a reliable way to make sure nothing is forgotten and nothing is released twice.

The point

A program must return the memory it uses. Doing it by hand is fast but error-prone; a background collector is safe but costs runtime. Giving each value a single owner, and cleaning it up when the owner is done, gets the safety without the runtime cost, at the price of being explicit about who owns what. And that same ownership idea keeps any kind of resource from being leaked or double-released.
