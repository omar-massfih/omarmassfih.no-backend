Systems need credentials: passwords, keys, tokens that let them talk to other systems. The single most important rule about these is also the most often broken: never put them in plain text in your code or version control. Doing so is not a small risk; it is treating the secret as already leaked.

Why plain text in a repo is so bad

A secret sitting in plain text in version control is exposed to everyone and every machine that can see the repository. That is usually far more people and places than you picture, and it includes the entire history: even if you delete the secret later, it lives on in past versions.

Worse, you cannot easily take it back. Once a secret has been copied out to every clone of the repository, revoking it is a scramble, and until you do, anyone who saw it can keep using it. A leaked secret is not undone by editing a file; the only real fix is to replace the secret everywhere, which is painful. So the goal is to keep it out of the code entirely.

Two safer ways

There are two common approaches. One is to store the secrets encrypted, versioned right alongside the code. This keeps them together with what uses them, but it moves the problem: now you have to guard the key that unlocks them, a secret protecting other secrets, and rotating or revoking access is awkward.

The other is to keep secrets in a dedicated service that hands them out when needed, rather than storing them with the code at all. This adds an external dependency and some complexity, but it usually gives you real advantages: a log of who accessed what, easy rotation, and quick revocation when something is compromised.

The leak you forget about

There is a subtle trap that applies no matter how carefully you fetch a secret. Even if the secret never touches your code, it can still end up in the files your tools produce along the way, the records of what they did, the saved plans of intended changes. A secret can quietly land in those byproducts in plain text. So those outputs have to be guarded and access-limited just as strictly as the secret itself, or you have simply moved the leak.

The point

Treat a secret placed in your code or version control as already leaked: it is exposed widely, preserved in history, and painful to revoke. Keep secrets out of the code, either encrypted with a carefully guarded key or served by a dedicated store with logging and easy rotation. And remember that secrets can seep into the files your tools generate, so protect those too.
