When you automate setting up servers, networks, and databases, there are two styles you can write in. One lists the steps to take. The other describes the result you want. They feel similar at first, but one of them ages far better than the other, and the reason is worth understanding.

Steps versus destination

The step-by-step style spells out actions in order: create this server, then attach that disk, then change this setting. You are writing directions, like a recipe.

The other style describes the destination: "I want three servers of this size, on this network, with this database." You do not say how to get there. A tool reads your description, compares it to what already exists, and works out the actions needed to make reality match. You state the end state; it figures out the route.

Why directions get brittle

The trouble with directions is that they secretly depend on your starting point. "Create this server" is the right step only if the server does not already exist. Run the same script again and it may fail, or make a duplicate, because the world is no longer in the state the steps assumed. Directions are tangled up with the history of what has already happened.

That makes them hard to reuse and hard to reason about. To know what a script will do, you have to know the exact state of things before it runs. As the number of steps and the number of possible starting states grow, that becomes a guessing game.

Why a destination stays clean

A description of the end state has no such baggage. It simply says what should be true. Whether you are starting from nothing, from a half-built setup, or from a complete one, the same description applies, because the tool computes the difference each time and does only what is needed. Run it against an empty world and it builds everything; run it again and it does nothing, because reality already matches.

This is why the destination style reads like the current desired reality rather than a diary of changes. You can look at it and know what the system is supposed to be, without replaying every step that got you there.

The takeaway

Automating infrastructure by listing steps ties your code to the exact situation it runs in, so it is fragile and awkward to reuse. Describing the end state you want, and letting a tool work out the steps, gives you code that means the same thing no matter where you start from. Write down the destination, not the directions, and the tool handles the route.
